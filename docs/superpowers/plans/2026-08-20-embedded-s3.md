# Embedded S3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship an S3-compatible store inside the self-hosted image so Vault becomes possible and web-ui's poster cache, user subtitles and thumbnails stop being silently disabled — while leaving an external S3 fully usable instead.

**Architecture:** versitygw runs as one more s6 longrun over a new `/storage` volume, listening on 127.0.0.1:8099 and never published through nginx. Credentials are generated on first start the way the API key already is. Buckets are directories, so provisioning is `mkdir`. `USE_LOCALS3=false` skips the service and lets the existing `AWS_*` variables point at someone else's S3.

**Tech Stack:** versitygw (Apache 2.0, Go, static binary), s6-overlay v3, Alpine, existing `aws-sdk-go v1.55.8` consumers.

**Spec:** `docs/superpowers/specs/2026-08-20-embedded-s3-design.md`

## Global Constraints

- **Existing installations must not break.** `/data` and `/pgdata` keep their current meaning and paths. `/storage` is new and additive; a user who never mounts it sees no change beyond the features they did not have.
- versitygw is pinned by tag **and** digest, exactly like every other component: `ghcr.io/versity/versitygw:latest@sha256:c4cbd9d9cb8dedbb055ac788dbd02635651b9b1cebac95b095b3217231aa87ad`. The binary lives at `/usr/local/bin/versitygw` inside that image and is statically linked (verified).
- The S3 port is **8099** — the next free one after nginx-vod's 8098 (verified against `common.template.env`).
- The service binds **127.0.0.1 only**. It must never appear in `etc/nginx/conf/nginx.template.conf`.
- Credentials come from `/etc/webtor/secrets/s3.env`, written mode **600**, generated once and reused across restarts, overridable from the environment — the same contract `generate-api-key-and-secret` already implements.
- versitygw's posix backend **requires xattr support** and exits otherwise. A bind mount from macOS or Windows does not have it. The run script must detect this and refuse with an explanatory line rather than crash-looping.
- Buckets are directories in the storage root, so provisioning uses `mkdir -p` and needs no S3 client. The image ships neither `aws` nor `mc`.

### Task 2: Generate S3 credentials on first start

**Files:**
- Create: `s6-overlay/scripts/generate-s3-credentials`
- Create: `s6-overlay/s6-rc.d/generate-s3-credentials/type`, `.../up`, `.../dependencies.d/base`
- Create: `s6-overlay/s6-rc.d/user/contents.d/generate-s3-credentials`

**Interfaces:**
- Consumes: nothing.
- Produces: `/etc/webtor/secrets/s3.env` containing `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, mode 600. Later tasks source it.

Follow `s6-overlay/scripts/generate-api-key-and-secret` exactly — same shape, same logging idiom, same "env wins, then existing file, then generate" order.

- [ ] **Step 1: Write the script**

Create `s6-overlay/scripts/generate-s3-credentials`:

```sh
#!/command/with-contenv sh

log() {
   echo "$1" | s6-log p"[generate-s3-credentials]" 1
}

f=/etc/webtor/secrets/s3.env
mkdir -p "$(dirname "$f")"
if [ -n "$AWS_ACCESS_KEY_ID" ] && [ -n "$AWS_SECRET_ACCESS_KEY" ]; then
  log "using provided AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY"
  key=$AWS_ACCESS_KEY_ID
  secret=$AWS_SECRET_ACCESS_KEY
elif [ -f $f ]; then
  log "credentials file ${f} already exists"
  exit
else
  log "generating S3 credentials"
  key=$(uuidgen | tr -d '-' | head -c 20)
  secret=$(uuidgen | sha1sum | head -c 40)
fi
log "storing S3 credentials to ${f}"
umask 077
echo "AWS_ACCESS_KEY_ID=${key}" > $f
echo "AWS_SECRET_ACCESS_KEY=${secret}" >> $f
chmod 600 $f
```

Note the `umask 077` **and** the explicit `chmod`: the redirect creates the file before `chmod` runs, so without the umask there is a window where it is world-readable. The existing `generate-api-key-and-secret` has that window; do not copy the flaw.

```bash
chmod +x s6-overlay/scripts/generate-s3-credentials
```

- [ ] **Step 2: Register the oneshot**

```bash
mkdir -p s6-overlay/s6-rc.d/generate-s3-credentials/dependencies.d
printf 'oneshot' > s6-overlay/s6-rc.d/generate-s3-credentials/type
printf '/etc/s6-overlay/scripts/generate-s3-credentials 2>&1' > s6-overlay/s6-rc.d/generate-s3-credentials/up
touch s6-overlay/s6-rc.d/generate-s3-credentials/dependencies.d/base
touch s6-overlay/s6-rc.d/user/contents.d/generate-s3-credentials
```

- [ ] **Step 3: Verify against a live container**

```bash

sleep 20
```

Expected: mode `-rw-------`, two non-empty variables.

Then verify persistence and the env override:
```bash

docker exec s3probe cat /etc/webtor/secrets/s3.env
```
Expected: identical values — a regenerated secret would invalidate every stored object reference.

### Task 3: Run the S3 service

**Files:**
- Create: `s6-overlay/s6-rc.d/s3/type`, `.../run`, `.../dependencies.d/base`, `.../dependencies.d/generate-s3-credentials`
- Create: `s6-overlay/s6-rc.d/user/contents.d/s3`
- Modify: `etc/webtor/common.template.env`

**Interfaces:**
- Consumes: `/etc/webtor/secrets/s3.env` from Task 2.
- Produces: an S3 endpoint at `127.0.0.1:8099`, and these variables for later tasks and for web-ui: `S3_SERVICE_HOST`, `S3_SERVICE_PORT`, `STORAGE_DIR`, `USE_LOCALS3`.

- [ ] **Step 1: Add the variables**

In `etc/webtor/common.template.env`, add:

```
STORAGE_DIR=${STORAGE_DIR:-/storage}
S3_SERVICE_HOST=127.0.0.1
S3_SERVICE_PORT=8099
USE_LOCALS3=${USE_LOCALS3:-true}
```

In the same file, fix the existing line `DATA_DIR=/data` to `DATA_DIR=${DATA_DIR:-/data}` — it is documented as configurable but currently is not, so an operator who wants the cache elsewhere cannot move it.

- [ ] **Step 2: Write the run script**

Create `s6-overlay/s6-rc.d/s3/run`:

```sh
#!/command/with-contenv sh
set -a
source /etc/webtor/common.env
source /etc/webtor/secrets/s3.env
set +a

log() {
  echo "$1" | s6-log p"[s3]" 1
}

if [ "${USE_LOCALS3:-true}" = "false" ]; then
  log "USE_LOCALS3=false -- not starting the built-in S3; set AWS_ENDPOINT to your own"
  # s6 restarts a longrun that exits, so idle rather than exiting.
  exec sleep infinity
fi

mkdir -p "$STORAGE_DIR"

# versitygw's posix backend keeps object metadata -- etag, content type,
# checksums, multipart state -- in extended attributes, and exits if the
# filesystem cannot store them. That is the case for a bind mount from macOS
# or Windows, and for some network filesystems on Linux. Say so plainly here
# instead of crash-looping with "xattr check failed" every second.
probe="$STORAGE_DIR/.xattr-probe"
: > "$probe"
if ! setfattr -n user.webtor -v probe "$probe" 2>/dev/null; then
  rm -f "$probe"
  log "FATAL: $STORAGE_DIR does not support extended attributes, which the S3 store requires."
  log "Mount it as a named docker volume (-v storage:/storage) rather than a host directory,"
  log "or set USE_LOCALS3=false and point AWS_ENDPOINT at an external S3."
  exec sleep infinity
fi
rm -f "$probe"

exec /app/versitygw \
  --port "$S3_SERVICE_HOST:$S3_SERVICE_PORT" \
  --access "$AWS_ACCESS_KEY_ID" \
  --secret "$AWS_SECRET_ACCESS_KEY" \
  posix "$STORAGE_DIR" 2>&1 | s6-log p"[s3]" 1
```

`setfattr` comes from the `attr` package — add `attr` to the `apk add` line in `Dockerfile`.

- [ ] **Step 3: Register the service**

```bash
mkdir -p s6-overlay/s6-rc.d/s3/dependencies.d
printf 'longrun' > s6-overlay/s6-rc.d/s3/type
touch s6-overlay/s6-rc.d/s3/dependencies.d/base
touch s6-overlay/s6-rc.d/s3/dependencies.d/generate-s3-credentials
touch s6-overlay/s6-rc.d/user/contents.d/s3
chmod +x s6-overlay/s6-rc.d/s3/run
```

- [ ] **Step 4: Verify it serves**

```bash

docker rm -f s3probe; docker run -d --name s3probe -p 18082:8080 -v s3probe-storage:/storage webtor-self-hosted:s3

```
Expected: the service is listed, and the endpoint answers (an S3 error document for an unsigned request is a pass — it proves the server is live).

- [ ] **Step 5: Verify the xattr guard fires**

```bash

docker run -d --name s3probe-bind -v /tmp/s3-bind:/storage webtor-self-hosted:s3
```

- [ ] **Step 6: Verify USE_LOCALS3=false**

Expected: the log line appears and nothing listens on 8099.

### Task 4: Provision buckets and wire web-ui

**Files:**
- Modify: `s6-overlay/scripts/generate-s3-credentials` (bucket creation) **or** create `s6-overlay/scripts/create-s3-buckets` with its own oneshot — the implementer chooses and explains
- Modify: `etc/webtor/common.template.env`
- Modify: `s6-overlay/s6-rc.d/web-ui/run`

**Interfaces:**
- Consumes: `STORAGE_DIR`, the credentials file, the S3 endpoint from Task 3.
- Produces: four buckets, and web-ui configured to use them.

- [ ] **Step 1: Create the buckets**

A bucket is a directory in the storage root — verified: directories created with `mkdir` before startup are returned by `ListBuckets`. So provisioning is:

```sh
for b in vault posters subtitles thumbnails; do
  mkdir -p "$STORAGE_DIR/$b"
done
```

This must run before web-ui and vault use them, and must be idempotent (it is, by `mkdir -p`). Put it wherever it reads most clearly — either extend the credentials oneshot or add a second one that depends on it — and say in the report which you chose and why.

- [ ] **Step 2: Point web-ui at the store**

In `etc/webtor/common.template.env`, add:

```
AWS_ENDPOINT=${AWS_ENDPOINT:-http://127.0.0.1:8099}
AWS_REGION=${AWS_REGION:-us-east-1}
AWS_NO_SSL=${AWS_NO_SSL:-true}
AWS_POSTER_CACHE_BUCKET=${AWS_POSTER_CACHE_BUCKET:-posters}
AWS_USER_SUBTITLE_BUCKET=${AWS_USER_SUBTITLE_BUCKET:-subtitles}
AWS_THUMBNAIL_BUCKET=${AWS_THUMBNAIL_BUCKET:-thumbnails}
```

Every one defaults to the built-in store and is overridable, so pointing at an
external S3 is a matter of setting `AWS_ENDPOINT` and the credentials.

In `s6-overlay/s6-rc.d/web-ui/run`, source the credentials after `api.env`:

```sh
source /etc/webtor/secrets/s3.env
```

web-ui reads `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` through
common-services' standard S3 client flags, so nothing else is needed.

- [ ] **Step 3: Verify web-ui actually reaches the store**

The honest end-to-end check is user subtitles: it is the one of the three
features that needs no external API key.

```bash
docker build -t webtor-self-hosted:s3 .
docker rm -f s3probe; docker run -d --name s3probe -p 18082:8080 -v s3probe-storage:/storage webtor-self-hosted:s3
sleep 25
docker exec s3probe sh -c 'ls /storage'
docker logs s3probe 2>&1 | grep -iE 's3|aws' | head -5
```
Expected: the four bucket directories exist, and web-ui logs no S3 configuration error.

Then confirm an object round-trips by writing one through the S3 API with the
generated credentials and reading it back — use the probe approach from the
spike (a small Go program using `aws-sdk-go v1.55.8`, run from the host against
the published port) or any equivalent you can justify. Do not claim the feature
works without having moved a byte through it.

- [ ] **Step 1: README**

Add a storage section covering, in the user's language:

## Order and dependencies

Tasks 1-4 are strictly sequential: each builds on the artifact the previous one puts in the image. Task 5 needs all of them. Task 6 can be written any time after Task 4 but should land last so it describes what actually shipped.

Vault is **not** in this plan. It is the next sub-project, and it brings its own service, its own migrations and the `vault reap` job the cron mechanism is already able to run.
