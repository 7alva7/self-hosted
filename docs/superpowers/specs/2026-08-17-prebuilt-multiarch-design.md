# Self-hosted: сборка из готовых multi-arch образов + e2e-тесты

Дата: 2026-08-17
Статус: утверждено (дизайн), ожидает план имплементации

## Проблемы

1. Self-hosted компилирует все 11 Go-сервисов + npm-фронтенд + nginx с Kaltura-модулями из исходников при каждой сборке (~40+ минут), хотя каждый компонент уже публикует собранный образ в GHCR.
2. Пины `*_COMMIT` в Dockerfile отстали от мейнов компонентов на много месяцев; процесс обновления ручной и не выполняется.
3. Нет ARM-поддержки (частый запрос пользователей): компонентные CI собирают только linux/amd64, s6-overlay в Dockerfile захардкожен на x86_64.

## Решение (утверждено)

Self-hosted перестаёт компилировать код. Dockerfile становится «сборочным»: артефакты копируются из готовых multi-arch образов компонентов. Версии пинятся дайджестами и бампаются автоматикой (Renovate), каждый бамп проверяется e2e-смоуком в CI на amd64 и arm64.

Утверждённые параметры:
- Меняем CI всех ~12 компонентных репозиториев (переиспользуемый workflow).
- Платформы: linux/amd64 + linux/arm64 (armv7 — нет).
- Версии: пин `tag@sha256:digest` + автобамп-PR через Renovate.

## Разведанные факты (2026-08-17)

- Все 11 Go-компонентов публикуют образы в `ghcr.io/webtor-io/<svc>` (`:latest`, `:master`, `:sha-*`, semver при `v*`) — только linux/amd64. В CI нет `platforms:`/buildx.
- `nginx-vod`: репо с Dockerfile существует (финальный образ несёт `/usr/local/nginx`), но CI не публикует образ вообще.
- Внутри всех Go-образов бинарь называется `server`; лежит в `/` (большинство) или в `/app` (web-ui, content-transcoder). Финальные стейджи без WORKDIR кладут в корень — при имплементации выверять по каждому Dockerfile.
- `web-ui` образ несёт всё, что self-hosted собирает npm'ом: `templates/`, `migrations/`, `pub/`, `assets/dist` (+ ffmpeg для thumbnails — в self-hosted base ffmpeg уже есть).
- `content-transcoder` образ дополнительно несёт `player/` (новое относительно нашего пина) и базируется на `jrottenberg/ffmpeg:8-alpine` — проверено, база мультиарховая (amd64+arm64).
- CGO-компоненты: `torrent-web-seeder` (static CGO), `srt2vtt`. Под QEMU их arm64-сборка может занимать 30–60 мин.
- Alpine-пакеты рантайма self-hosted (redis, ffmpeg, postgresql, envsubst и пр.) мультиарховые из коробки.
- GitHub Actions предоставляет бесплатные нативные arm64-раннеры (`ubuntu-24.04-arm`) для публичных репозиториев.

## Фаза 1 — CI компонентов (12 репо)

1. Переиспользуемый workflow в `webtor-io/.github` (стандартное место для org-wide reusable workflows): QEMU + buildx, `platforms: linux/amd64,linux/arm64`, metadata-action теги как сейчас (branch, semver, sha).
2. Каждый компонентный workflow → ~10 строк вызова reusable.
3. Первый — `nginx-vod` (включить публикацию образа).
4. Dockerfile'ы компонентов на первом проходе не трогаем (чистый QEMU). Если CGO-компоненты собираются неприемлемо долго — точечно переводим их на кросс-компиляцию (`FROM --platform=$BUILDPLATFORM` + musl-toolchain). Не оптимизировать заранее.

## Фаза 2 — self-hosted Dockerfile

1. 11 build-стейджей + npm-стейдж + nginx-стейдж → `FROM ghcr.io/webtor-io/<svc>:<tag>@sha256:<digest> AS <svc>` и `COPY --from=<svc>` с переименованием `server` → имя сервиса (пути под наши s6 run-скрипты).
2. Из `web-ui`: бинарь + `templates/`, `pub/`, `migrations/`, `assets/dist`. Из `content-transcoder`: бинарь + `player/`. Из `nginx-vod`: `/usr/local/nginx` (наш `nginx.template.conf` остаётся).
3. s6-overlay: `ARG TARGETARCH` → маппинг amd64→x86_64, arm64→aarch64.
4. CI self-hosted: buildx `linux/amd64,linux/arm64` (сборка теперь assembly-only, быстрая).
5. Провенанс: вместо `*.commit`-файлов — OCI-лейблы с тегами/дайджестами компонентов.
6. Renovate-конфиг: pinDigests для `FROM ghcr.io/webtor-io/*` — PR на каждый новый образ компонента.

## Тесты

Смысл: автобамп безопасен только если каждый PR проверяется автоматически. Тесты — часть той же работы, не «потом».

### Фикстура (детерминированная, без внешней сети и чужого контента)

- Тестовый контент генерируется скриптом: маленькое видео `ffmpeg -f lavfi -i testsrc` (+ аудиодорожка), текстовый файл, `.srt`-субтитры.
- Из контента создаётся `.torrent` с webseed (BEP19 `url-list`), указывающим на nginx-контейнер с этими файлами. `torrent-web-seeder` (anacrolix) умеет webseeds — пиры и трекеры не нужны.
- Окружение теста: docker compose — контейнер self-hosted + nginx-webseed.

### Сценарии смоука

1. Все s6-сервисы поднялись (readiness: `/` отвечает 200, в логах нет crash-loop).
2. Загрузка `.torrent` через UI/API → листинг файлов.
3. DDL: скачивание файла из торрента, checksum совпадает с фикстурой.
4. ZIP-архив торрента скачивается и распаковывается, состав совпадает.
5. HLS: манифест `index.m3u8` для тестового видео отдаётся, первый сегмент скачивается (проверяет цепочку transcoder → nginx-vod → proxy).
6. Субтитры: конвертация srt→vtt отдаёт валидный vtt.
7. Персистентность: рестарт контейнера с тем же `/pgdata` и `/data` — сервис поднимается, миграции идемпотентны.

### Прогон в CI

- Матрица: `ubuntu-latest` (amd64) + `ubuntu-24.04-arm` (arm64) — обе архитектуры нативно, без QEMU-рантайма.
- PR (включая Renovate-бампы): сборка образа под арху раннера + смоук. Push тега `v*`: то же + multi-arch push в GHCR.
- Тесты живут в этом репо (`tests/`), запускаются одним скриптом и локально: `tests/run.sh <image>`.

## Риски

1. **Прыжок версий.** Переход на текущие мейны — большой апгрейд всех компонентов разом: возможны переименованные env-переменные/флаги, изменения формата конфига torrent-http-proxy, толстая пачка миграций web-ui на embedded PG. Митигейт: e2e-смоук из этой же спеки; несовместимости чинятся в run-скриптах/шаблонах self-hosted по ходу.
2. **CGO под QEMU** (фаза 1): долгие arm64-сборки torrent-web-seeder/srt2vtt. Митигейт: принять или точечная кросс-компиляция.
3. **Разные базы компонентов** (scratch, alpine разных версий, ffmpeg-образ): копируем только статические бинари и статические ассеты — зависимость от базы компонента отсутствует. Проверяется смоуком.
4. **`:latest` без semver у части компонентов**: Renovate бампает дайджест latest — приемлемо; при желании компоненты позже переходят на v-теги без изменений схемы.

## Порядок работ

1. Reusable workflow → раскатка по 12 репо (nginx-vod первый).
2. Дождаться зелёных multi-arch образов.
3. Тестовая обвязка в self-hosted (`tests/`): фикстура + смоук-скрипт (можно писать параллельно с п.1, гонять на текущем amd64-образе).
4. Переписать Dockerfile self-hosted + s6 arch-fix; смоук amd64.
5. Смоук arm64 (CI `ubuntu-24.04-arm` + локально на Apple Silicon).
6. Renovate-конфиг.
7. Релиз-тег, README: заявить ARM-поддержку.
