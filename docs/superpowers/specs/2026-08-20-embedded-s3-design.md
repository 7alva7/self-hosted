# Встроенный S3 в self-hosted образе

Дата: 2026-08-20
Статус: черновик, ожидает рецензии владельца
Репозиторий: `self-hosted` (правки в `web-ui` не требуются)

## Задача

В проде на S3 завязаны три потребителя: `vault` (файлы пользователей), `web-ui`
(кэш постеров, пользовательские субтитры, миниатюры) и `s3-cache` (в образ не
входит). В self-hosted S3 нет вообще, поэтому Vault невозможен, а три функции
web-ui молча выключены.

Цель: поднять в образе S3-совместимое хранилище, оставив возможность указать
внешний S3 вместо него.

## Выбор реализации: versitygw

Кандидаты сравнивались по лицензии, размеру и модели хранения:

| | Лицензия | Бинарник | Модель |
|---|---|---|---|
| **versitygw** | Apache 2.0 | 50 МБ | шлюз поверх обычной ФС |
| SeaweedFS | Apache 2.0 | 197 МБ | собственное хранилище |
| Garage | AGPL | — | собственное хранилище |
| MinIO | AGPL, с 2025 в maintenance | — | собственное хранилище |

AGPL исключён: продукт устанавливают на свои машины, лицензионный риск не нужен.
MinIO вдобавок деградировал как проект.

Из двух Apache-кандидатов выбран versitygw: объекты остаются обычными файлами на
диске (у SeaweedFS данные лежат в собственных volume-файлах и без него не
читаются), вчетверо меньше по размеру и запускается одним процессом с одним
аргументом — против четырёх подсистем SeaweedFS в контейнере, где уже
одиннадцать сервисов.

## Что проверено спайком

Проба тем же `aws-sdk-go v1.55.8`, которым ходят vault и web-ui: 21 проверка,
0 отказов. Включая операции, на которых совместимость обычно обрывается:

- `GetObject` с заголовком Range (Vault читает куски именно так);
- полный цикл multipart: `CreateMultipartUpload`, `UploadPart` ×2, `ListParts`,
  `ListMultipartUploads`, `CompleteMultipartUpload` — размер собранного объекта
  совпал с исходным;
- `AbortMultipartUpload` — на него опирается сборщик мусора Vault;
- presigned GET и presigned GET с Range (вернул корректный 206).

## Ограничение, найденное спайком: xattrs

Posix-бэкенд versitygw хранит метаданные объектов (ETag, content-type,
контрольные суммы, сведения о multipart) в расширенных атрибутах файлов и
**отказывается стартовать на файловой системе без их поддержки**:

```
xattr check failed: xattrs are not supported on this filesystem
```

На именованном docker-томе всё работает — там файловая система Linux-виртуалки.
На bind-mount с macOS или Windows — нет. На Linux отказ возможен на части сетевых
ФС.

Решение: run-скрипт проверяет поддержку xattrs до запуска и при отсутствии
пишет внятную строку и не поднимает сервис, вместо падения с непонятной ошибкой.
README требует именованный том для `/storage`.

Следствие для переноса данных: `cp` без сохранения xattrs теряет метаданные.
Документируем `rsync -X`, `cp -a`, `tar --xattrs`.

## Раскладка каталогов

Ломать существующие установки не будем. Добавляется одна директория:

| Путь | Что | Изменение |
|---|---|---|
| `/data` | кэш торрентов | без изменений |
| `/pgdata` | база | без изменений |
| `/storage` | постоянное хранилище S3 | новое |

Имя `/storage`, а не `/s3`: описывает назначение, а не реализацию, и переживёт
замену сервера или переключение на внешний endpoint.

Смысловое разделение уходит в README: `/data` — расходуемый кэш, его потеря не
страшна; `/storage` и `/pgdata` — то, что теряется навсегда.

Побочно: `DATA_DIR=/data` в `common.template.env` записан без `${...:-}` и потому
снаружи не переопределяется. Исправляем на `${DATA_DIR:-/data}`, чтобы обещание
настраиваемости стало правдой — тогда желающие смогут получить и раскладку
`cache`/`db`/`storage` своими силами.

## Сервис в образе

Новый s6-сервис `s3` (longrun) по образцу существующих: `type`, `run`,
`dependencies.d/base`, регистрация в `user/contents.d/s3`.

Запуск: `versitygw posix /storage` на `S3_SERVICE_PORT` (по умолчанию 8099,
следующий свободный в карте портов). Слушает только 127.0.0.1 — наружу через
nginx не публикуется: доступ к S3 у web-ui и vault внутренний.

Учётные данные генерируются при первом старте по образцу
`generate-api-key-and-secret`: oneshot-сервис `generate-s3-credentials` пишет
`/etc/webtor/secrets/s3.env` с `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`,
переживает рестарт, и переменные окружения имеют приоритет, если заданы снаружи.
Файл создаётся с правами 600.

Бакеты создаются тем же oneshot: `vault`, `posters`, `subtitles`,
`thumbnails`. У posix-бэкенда бакет — это каталог в корне хранилища, что
проверено: созданные `mkdir` до старта каталоги versitygw отдаёт как бакеты в
`ListBuckets`. Поэтому создание — обычный `mkdir -p`, идемпотентный по
определению, и S3-клиент в образе не нужен (его там и нет: ни `aws`, ни `mc`,
а подписывать SigV4 голым curl непрактично).

## Переключение на внешний S3

Никакой новой механики не требуется: потребители уже читают стандартные
`AWS_ENDPOINT`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`,
`AWS_NO_SSL`. Вводится `USE_LOCALS3` (по умолчанию `true`) по образцу
существующего `USE_LOCALPG`: при `false` встроенный сервис не стартует, а
переменные `AWS_*` берутся снаружи.

## Что включается следом

`vault` в этот спек **не входит** — он отдельный подпроект со своим сервисом,
своими миграциями и задачей `vault reap`, которую крон уже готов принять.

В web-ui три функции включаются заданием бакетов: постеры
(`AWS_POSTER_CACHE_BUCKET`), пользовательские субтитры
(`AWS_USER_SUBTITLE_BUCKET`), миниатюры (`AWS_THUMBNAIL_BUCKET`). Код уже
устроен так, что при незаданном бакете сервис равен nil и функция скрывается
(`serve.go:511`), поэтому включение — вопрос переменных, а не правок кода.

## Проверка

Смоук-сценарий `70-s3.sh`:

- сервис `s3` присутствует в списке s6 после старта;
- четыре бакета созданы;
- запись, чтение и удаление объекта через web-ui — проверяется загрузкой
  пользовательских субтитров, единственной из трёх функций, которую можно
  прогнать без внешних API-ключей;
- при `USE_LOCALS3=false` и незаданном `AWS_ENDPOINT` сервис не стартует, а
  инстанс продолжает работать (S3-функции просто выключены).

Негативный контроль: удалить проверку xattrs и убедиться, что сценарий на
файловой системе без их поддержки краснеет по-другому — то есть проверка
действительно ловит именно этот случай.

## Риски

1. **versitygw моложе альтернатив** — одна раскрытая уязвимость за три года
   против нуля у SeaweedFS и Garage. Митигейт: сервис слушает только localhost и
   наружу не выставляется.
2. **Прирост образа ~49 МБ** — измерено тремя способами, сходящимися на одном
   числе: размер слоя `COPY versitygw` по `docker history`, размер самого файла
   внутри контейнера и разница распакованных итогов (636.5 -> 685.5 МБ). Это
   **около 7.7%**.

   Осторожно с процентами: `docker image inspect .Size` на машинах с
   containerd-snapshotter отдаёт *сжатый* размер (214 -> 236 МБ), и деление
   распакованной дельты на сжатую базу даёт завышенные 23% — эта ошибка была в
   первой редакции спеки. Сжатая дельта (~22 МБ) — это то, что платится
   трафиком при `docker pull`; распакованная (~49 МБ) — то, что занимает диск.

   SeaweedFS по той же мерке стоил бы 197 МБ. При `USE_LOCALS3=false` бинарник
   всё равно лежит в образе — выносить его в отдельный образ ради этого не
   стоит усложнения сборки.
3. **Зависимость от xattrs** — описана выше, закрывается проверкой при старте и
   документацией.
4. **Совместимость проверена спайком, но не под нагрузкой.** Vault загружает
   файлы кусками по многу мегабайт; спайк гонял 5 МиБ. Поведение на больших
   объёмах и при параллельных загрузках остаётся непроверенным до включения
   Vault.
